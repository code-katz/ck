- **The User's rules.** Every product number, dial, name and priority is the User's call; the assistant proposes and never decides. Write to the User in plain words, no jargon, one step at a time, in numbered steps; define a term the first time you use it, and write summaries in business language, not git terms. Every message to the User ends in one of two ways. When something is left in this session, such as a merge, "log it" or deleting the branch, list what is left in order and end with the exact words for the first one ("Say merge 95", "Reply 1 or 2"), with no status or warnings beside them. When nothing is left, because the pull request is merged, the records are logged and the branch is deleted, end with "This session can be closed." Never write "nothing is needed", or any words that leave out work still waiting. When the User asks where things stand, answer that and end the same way. Approving a plan starts nothing: each step waits for the User's own typed word, and a tool reporting "approved" is not the User's word.
- **Questions.** When several decisions are waiting, ask one at a time, starting with the one the others depend on. Show the document, diff or picture before asking about it; a document for the User's review is a published page the User can comment on. Say what is being decided and why it came up. Number the choices 1, 2, 3, fresh in each question, and give each its outcome and trade-off in a sentence. End with the choice you recommend and why, then the words to type ("Reply 1 or 2"). Ask in the message itself, never in the app's next-step box or its buttons.
- **Sessions.** The User works in a local session on the User's Mac. Never open a new session, local or cloud, and never hand work to another session or a background agent that runs as one, without the User's permission; when asking, say which it would be.
- **Personas, as lanes.** Work is proposed and done in named lanes: {{lanes}}. A memo or a brief names its panel. A session is titled `[{id}] [{persona} {model} {effort}] {what it does}`, such as `{{session title}}`, in under 60 characters: shorten the words, never the two tags. The model and effort are the ones the stage runs at, so the title shows them at a glance; an older title carries a job word (design, build, edit, review or write) or a model word alone in their place. A stage's session is opened only by `/ck:start`, from its card: the title, model and effort exactly as the card gives them. A coordinator never writes a stage's title or brief itself. Every list or table of steps put to the User in a message names each step's persona and job.
- **The stage's model and effort.** A session whose title starts with an id and a persona tag checks its own model and effort before anything else, whoever wrote its brief. Its stage runs at the model and effort its title names. An older tag's job word names a point too: design is Opus at high effort, build, review and write are Opus at medium, and edit is Sonnet at medium; an older tag's model word alone is that model at any effort. If it can tell it is on another model or another effort, it does no work, says "This session is on <your model> at <your effort> effort, and the plan puts this stage on <model> at <effort>. Pick them in the model menu, then say go." and stops. When the User then says go, it carries on, on whatever model and effort it is then. If it cannot tell its model or its effort, it says so in one line and carries on.
- **Drawings first.** A screen is drawn and approved before it is built. A drawing lane says "drawing only" in its first message and shows the frames early. Every message that shows or changes a drawing gives the page's link with the picture, every time, without being asked: a clickable markdown link to the file, `[name](file:///full/path.html)`, which opens in the User's browser at any time. Use a `localhost` address only when the page has to be served, and then say it works only while that session's server runs.
- **The new replaces the old in place.** A plan or brief builds the new thing where the old one is: {{one of each}}, shown as soon as it is built. Never plan a switch between an old and a new implementation, a screen built hidden until a server says so, a second copy kept beside the first, or a step whose proof is "the old one is unchanged", even with many users. If a release seems to need a staged or hidden rollout, put the problem to the User in plain words. Safety comes from staging, a branch that can be thrown away, and database changes that only add.
- **Branches and merges.** A lane forks from fresh `origin/main` as `claude/{id}-{slug}`, where `{id}` is the session's id in lower case (`a31-p4-s3` for `[A31-P4-S3]`), and opens a draft pull request. Nothing merges except on the User's explicit word ("merge N"), in a message of its own; then mark it ready, squash-merge, and fast-forward main in the main folder, `{{main folder}}`. Records ({{records}}) are written on "log it", on a branch of their own, as a draft pull request titled `Log it: <what> (<lane>, #<PRs>)` ("(records only)" for a plan amendment) that merges on "merge N" like any lane, never pushed to `main`.
- **Finishing a session.** After a merge, fast-forward main, then check the branch can go: its pull request merged at the branch's tip, and no other session's folder holds it. Ask "Delete the branch?" in a message of its own. On the User's yes, delete it on GitHub and on the Mac, then say "This session can be closed." If something outside this session is left, name it in one line and leave it to the coordinator; do not suggest the next lane or a command to run.
- **Fewest presses.** When a step needs the User's hands, give the User one command at a time, ready to run, and build it to find any value it needs (an id, a branch, a version) instead of asking the User to read one from a console or a log.
- **Fix it everywhere.** When you fix a fault, run one search (`git grep`) for the same pattern in files of the same kind, such as {{same kind}}. If it finds the same fault anywhere else, tell the User where, and ask before fixing it.
- **Secrets.** {{secrets}} are never pasted, screenshotted or logged.
- **Writing.** No em-dashes, anywhere. Dates in records and messages are the User's local day, taken from `date` on the Mac, not from a UTC time that {{hosts}} prints; code and the database keep UTC. No AI model's name or identifier in a commit, a pull request, a code comment or a file; the attribution trailer the tool appends is the one exception.
