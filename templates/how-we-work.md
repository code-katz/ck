- **The User's rules.** Every product number, dial, name and priority is the User's call; the assistant proposes and never decides. Write to the User in plain words, no jargon, one step at a time, in numbered steps; define a term the first time you use it, and write summaries in business language, not git terms. A message that needs something from the User ends with that one thing: the exact words to type ("Reply 1 or 2", "Say merge N"), with no status, warnings or later steps beside it. When the User asks where things stand, answer that and nothing else; when nothing is needed from the User, say so in those words. Approving a plan starts nothing: each step waits for the User's own typed word, and a tool reporting "approved" is not the User's word.
- **Questions.** When several decisions are waiting, ask one at a time, starting with the one the others depend on. Show the document, diff or picture before asking about it; a document for the User's review is a published page the User can comment on. Say what is being decided and why it came up. Number the choices 1, 2, 3, fresh in each question, and give each its outcome and trade-off in a sentence. End with the choice you recommend and why, then the words to type ("Reply 1 or 2").
- **Sessions.** The User works in a local session on the User's Mac. Never open a new session, local or cloud, and never hand work to another session or a background agent that runs as one, without the User's permission; when asking, say which it would be.
- **Personas, as lanes.** Work is proposed and done in named lanes, each owned by the persona that This project names for it. A memo or a brief names its panel.
- **Drawings first.** A screen is drawn and approved before it is built. A drawing lane says "drawing only" in its first message and shows the frames early.
- **Branches and merges.** A lane forks from fresh `origin/main` as `claude/{id}-{slug}`, where `{id}` is the session's id in lower case (`a31-p4-s3` for `[A31-P4-S3]`), and opens a draft pull request. Nothing merges except on the User's explicit word ("merge N"), in a message of its own; then mark it ready, squash-merge, fast-forward main in the main folder that This project names.
- **Finishing a session.** After a merge, fast-forward main, then check the branch can go: its pull request merged at the branch's tip, and no other session's folder holds it. Ask "Delete the branch?" in a message of its own. On the User's yes, delete it on GitHub and on the Mac, then say in one line that the session is finished and can be archived. If nothing else is left, say so; if something is, name it and who does it.
- **Fewest presses.** When a step needs the User's hands, give the User one command at a time, ready to run, and build it to find any value it needs (an id, a branch, a version) instead of asking the User to read one from a console or a log.
- **Fix it everywhere.** When you fix a fault, run one search (`git grep`) for the same pattern in files of the same kind, such as the other mockups. If it finds the same fault anywhere else, tell the User where, and ask before fixing it.
- **Secrets.** The secrets This project names are never pasted, screenshotted or logged.
- **Writing.** No em-dashes, anywhere. Dates in records and messages are the User's local day, taken from `date` on the Mac, not from a UTC time that GitHub or a server prints; code and the database keep UTC. No AI model's name or identifier in a commit, a pull request, a code comment or a file; the attribution trailer the tool appends is the one exception.
- **Records.** Decisions, priorities and finalized plans go in the records This project names, and records are written on "log it".
